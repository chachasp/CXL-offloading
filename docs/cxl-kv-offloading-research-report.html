KVBM + CXL NUMA KV Cache Offloading

조사·설계·구현 기준일 2026-08-12 · Dynamo v1.3.0 · Qwen3-30B-A3B-FP8

0. 요약

최종 선택은 KVBM + CXL System RAM/NUMA입니다. KVBM G2의 KV payload만 CXL memory-only node에 강제 배치하고 일반 DRAM fallback을 금지합니다. DRAM은 Dynamo, vLLM, PyTorch와 metadata 등 일반 실행 메모리에는 계속 사용됩니다.

현재 서버는 1 GPU/TP=1이며 향후 같은 CPU socket에 2 GPU/TP=2로 확장할 예정입니다. 코드는 두 경우를 고려하지만 H100/CXL 서버에서의 실제 검증은 아직 수행하지 못했습니다.

1. 공개 구현

LMCache에는 CXL을 포함할 수 있는 공식 Device-DAX backend가 있으나 공식 문서상 TP=1과 single-tensor chunk로 제한됩니다. KVBM은 G1 GPU → G2 pinned host → G3 disk → G4 object tier를 제공하지만 CXL NUMA node 강제 배치는 upstream에 없습니다. 따라서 본 저장소는 Dynamo v1.3.0 KVBM의 실제 allocator를 patch합니다.

2. Device-DAX와 System RAM/NUMA

항목Device-DAXSystem RAM/NUMA
접근/dev/daxX.Y mmap일반 virtual memory + NUMA policy
Kubernetesdevice hostPath 필요별도 CXL resource 불필요, Pod memory/cpuset 적용
KVBM G2신규 backend/tier 필요allocator 확장으로 연결 가능
TP=2rank-aware DAX 신규 개발KVBM tensor-parallel 구조 유지

따라서 이 구현은 Device-DAX를 사용하지 않습니다. CXL을 별도 memory-only NUMA node로 online해야 합니다.

3. KVBM vs. LMCache

조합현재 상태판정
LMCache + Device-DAX TP=1upstream backend 존재빠른 실험에는 가능
LMCache + Device-DAX TP=2공식 제한추가 개발 필요
KVBM + NUMA TP=1/2TP 구조 존재, CXL placement 없음선택: strict allocator 추가
KVBM + Device-DAXG1~G4에 raw DAX tier 없음범위가 가장 큼

DYN_KVBM_ENABLE_NUMA만으로 CXL node를 선택할 수 없습니다. 패치는 G2의 PinnedAllocator가 명시된 memory-only node를 사용하도록 변경합니다.

4. 데이터 경로와 Kubernetes 구성

GPU HBM / G1
      ↕ CUDA host-memory transfer
CXL System RAM memory-only NUMA node / G2 KV payload

DRAM: runtime + metadata + control buffers (KV offload tier로는 사용 안 함)

Kubernetes는 GPU 수, 총 memory request/limit, IPC_LOCK capability와 Pod lifecycle을 관리합니다. CXL 용량을 extended resource로 등록할 필요는 없습니다. 실제 page placement는 mmap → mbind → fault → move_pages 검증 → cuMemHostRegister로 결정합니다.

5. 승인 후 구현 단계

  1. CXL을 System RAM으로 전환하고 memory-only node 확인
  2. 64 MiB CUDA registration probe
  3. 고정 commit에 patch를 적용해 custom KVBM wheel/image build
  4. 64 GiB G2, TP=1 DGD 배포
  5. residency·correctness·stability 검증
  6. 128→256 GiB 확대
  7. 향후 두 GPU 장착 후 topology 재확인과 TP=2 검증

namespace 재구성, reboot와 mode 전환은 자동화하지 않습니다.

6. 검증·Benchmark와 위험

no-offload, DRAM G2, CXL G2를 동일 GPU 수 안에서 비교합니다. 지표는 requests/s, output tokens/s, p50/p99 TTFT, p50/p99 ITL, 오류율, KVBM hit/eviction, CXL 사용량과 bandwidth입니다.

위험대응
CXL zone의 long-term pin 불가64 MiB probe에서 중단; DRAM fallback 없음
잘못된 DRAM placement모든 page의 node를 검사하고 fail-fast
Pod memory limit 부족CXL G2 + runtime DRAM을 모두 반영
TP=2 PCIe 비대칭장착 후 rank별 topology/bandwidth 재측정
큰 pool 시작 지연64 GiB에서 시작해 단계적으로 확대

7. 결론

KVBM G2 KV payload를 CXL memory-only NUMA node에만 저장하는 방향으로 구현했습니다. 일반 DRAM을 offload cache로 사용하지 않으며, 배치나 CUDA 등록이 불확실하면 실행을 거부합니다. 이 결과는 실제 H100/CXL 서버 검증 전까지 실험적입니다.

근거: Linux CXL/DAX 및 memory hotplug 문서, Kubernetes resource/topology 문서, Dynamo v1.3.0 소스와 KVBM configuration, LMCache Device-DAX 공식 제한.
